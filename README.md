# Mini NPU Simulator

## 실행 방법

1. 저장소를 클론한 뒤, `mini_npu/` 폴더로 이동합니다.
2. `data.json`이 `main.py`와 같은 폴더에 있는지 확인합니다.
3. 다음 명령어로 실행합니다.
4. 모드를 선택합니다.
   - `1` — 3×3 필터 A/B와 패턴을 직접 입력하는 모드
   - `2` — data.json에 저장된 5×5/13×13/25×25 케이스를 일괄 분석하는 모드

## 파일 구조

mini_npu/
├── main.py # 메인 실행 파일 (모드 선택 및 전체 흐름 조립)
├── mac.py # MAC 연산 (곱셈-누적)

`main.py`가 진입점이며, 기능별로 모듈을 분리해 각 파일이 한 가지 책임만
담당하도록 구성했다.

## 구현 요약

### 모듈 구조
`main.py`는 모드 선택과 전체 흐름 조립만 담당하고, 실제 기능은 6개 파일
(`mac.py`, `io_console.py`, `judge.py`, `data_loader.py`, `labels.py`, `perf.py`)로
분리했다. 한 파일은 한 가지 책임만 지도록 나누어, 특정 기능(예: 성능 측정 표 서식)을
수정할 때 다른 기능(예: 판정 로직)에 영향을 주지 않도록 했다.

### 라벨 정규화
data.json의 expected 값('+', 'x')과 filters 키('cross', 'x')는 프로그램 내부
표준 라벨(Cross, X)과 표기가 다르다. 이를 그대로 비교하면 실제로는 정답이어도
문자열이 달라 항상 FAIL로 처리되는 문제가 생긴다. 따라서 labels.py에서
LABEL_MAP으로 모든 표기를 표준 라벨로 변환한 뒤에만 비교하도록 했다.

### MAC 연산
NumPy 등 외부 라이브러리 없이, 중첩 반복문으로 패턴과 필터의 같은 위치 값을
곱하고 누적하는 방식으로 구현했다(mac.py). 시간 복잡도는 O(N²)이며, 이는
성능 측정 결과로 뒷받침된다(아래 "성능 표 해석" 참고).

### 동점 처리 정책 (epsilon)
부동소수점 연산은 0.1 + 0.2 != 0.3처럼 미세한 오차를 갖는다. 실제로 data.json의
size_5_1 케이스에서 Cross 점수 0.9와 X 점수 0.8999999999999999처럼, 이론상
같아야 할 두 값이 계산 과정에서 미세하게 달라지는 사례가 확인되었다. 이를
단순 `==` 비교로 판정하면 실제로는 동점인 경우를 잘못 판정하게 되므로,
abs(a - b) < 1e-9 기준의 epsilon 비교를 적용해 동점(UNDECIDED)을 별도로
처리했다.

### 예외 처리
data.json을 찾을 수 없거나 형식이 깨진 경우, 필터 크기가 없는 경우, 패턴/필터
딕셔너리에 필요한 키가 없는 경우, 패턴과 필터의 크기가 일치하지 않는 경우를
각각 방어했다. 어느 경우든 프로그램 전체가 중단되지 않고 해당 케이스만
FAIL로 처리한 뒤 다음 케이스로 진행하도록 구현했다.

## 결과 리포트

### FAIL 케이스 원인 분석

data.json 모드(모드 2) 실행 결과, 총 6개 케이스 중 3개(size_5_2, size_13_1,
size_25_2)는 PASS, 3개(size_5_1, size_13_2, size_25_1)는 FAIL로 판정되었다.

FAIL이 발생한 3개 케이스는 모두 판정 결과가 UNDECIDED(동점)였다는 공통점이
있다. 예를 들어 size_5_1의 경우 Cross 점수는 0.9, X 점수는
0.8999999999999999로 계산되었는데, 두 값은 수학적으로 동일해야 하지만
부동소수점 연산 과정에서 미세한 오차가 발생해 서로 다른 값으로 나타났다.

이는 로직 오류가 아니라, epsilon(1e-9) 기반 동점 판정이 의도대로 정확히
동작한 결과다. abs(a - b) < 1e-9라는 기준으로 "사실상 같은 값"을 정확히
포착했기 때문에, expected에는 명확한 정답(X 또는 Cross)이 있었음에도
UNDECIDED로 판정되어 FAIL 처리되었다. 즉 이 3개의 FAIL은 데이터/스키마
문제도, 로직 버그도 아닌, "수치 비교의 근본적 한계에 대한 의도된 방어적
판정"으로 분류할 수 있다.

### 성능 표 해석 및 O(N²) 근거

| 크기    | 평균 시간(ms) | 연산 횟수(N²) |
|--------|--------------|--------------|
| 3×3    | 0.001        | 9            |
| 5×5    | 0.002        | 25           |
| 13×13  | 0.010        | 169          |
| 25×25  | 0.034        | 625          |

3×3에서 25×25로 갈 때 한 변의 크기는 약 8.3배(25÷3) 증가했지만, 평균 소요
시간은 34배(0.034÷0.001) 증가했다. 크기 증가율보다 시간 증가율이 훨씬 큰
것은, MAC 연산이 N에 선형으로 비례하는 것이 아니라 N²(연산 횟수)에 비례하기
때문이다. 실제로 연산 횟수 기준으로는 3×3(9회) 대비 25×25(625회)가 약
69배(625÷9) 늘었고, 이는 크기 증가율의 제곱(8.3² ≈ 69)과 거의 일치한다.
측정된 시간 증가율(34배)이 이론값(69배)보다 다소 작게 나타난 것은, 크기가
작을 때는 함수 호출 오버헤드 등 다른 요인이 상대적으로 크게 작용하기
때문으로 해석된다. 이러한 경향은 반복문 2개가 중첩되어 N번씩 도는
mac()의 구조(STEP 1)와 일치하며, MAC 연산의 시간 복잡도가 O(N²)임을
실측으로 뒷받침한다.

## 재현성

### 모드 1 (사용자 입력)
필터 A에 X 필터(`1 0 1 / 0 1 0 / 1 0 1`), 필터 B에 Cross 필터
(`0 1 0 / 1 1 1 / 0 1 0`), 패턴에 Cross 패턴(`0 1 0 / 1 1 1 / 0 1 0`)을
입력하면 다음과 같이 출력되어야 한다.
- A 점수: 1.0, B 점수: 5.0, 판정: B

행/열 개수가 3개가 아니거나 숫자가 아닌 값을 입력하면 오류 안내 후
같은 줄을 다시 입력받아야 한다.

### 모드 2 (data.json 분석)
`python3 main.py` 실행 후 `2`를 선택하면 다음 결과가 나와야 한다.
- 총 테스트: 6개 / 통과: 3개 / 실패: 3개
- 실패 케이스 3건은 모두 UNDECIDED(동점) 판정에 의한 것
- 크기별 평균 시간(3×3 → 25×25)이 대체로 증가하는 경향을 보여야 한다

data.json을 찾을 수 없거나 형식이 깨진 경우, 프로그램이 중단되지 않고
안내 메시지를 출력한 뒤 정상 종료되어야 한다.
